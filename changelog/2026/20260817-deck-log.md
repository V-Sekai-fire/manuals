# V-Sekai Multiplayer Fabric Deck Log — 2026-08-17 (Monday)

Date: 2026-08-17

The WebTransport contract has a second implementation, and it contradicted one claim the fabric makes about its own
wire before carrying a byte of real traffic. `transport-fanout` caps a subscriber's slice at 64 records and calls
6400 bytes "comfortably inside one message"; two stacks that share no code both put the limit at 11 records, and
`datasource-queen`'s own `WT_MTU_MAX` agrees with them rather than with the comment.

That is one finding rather than a pile, and the count is worth keeping honest. Building the pair also cost three
library defects — an EC key `pywebtransport` would not load, an iceoryx2 subscriber buffer that drops the oldest of
three sends, and an aioquic datagram queue that wedges on an oversized send. Those are real and none of them says
anything about the contract.

## Added

- [RFD 0123](https://v-sekai-multiplayer-fabric.github.io/multiplayer-fabric-manuals/rfd/0123-a-second-webtransport-implementation/),
  which puts a second implementation of the WebTransport contract on a stack sharing no code with the first. RFD 0088
  chose one QUIC stack on both ends, which buys interoperability by construction and gives up the check: a wire
  implemented once describes the program that implements it. Khronos ratifies against two independent implementations
  for the same reason.
- [transport-gateway-python](https://github.com/v-sekai-multiplayer-fabric/transport-gateway-python), the reliable half
  on `aioquic` 1.3.0, and
  [transport-ingest-python](https://github.com/v-sekai-multiplayer-fabric/transport-ingest-python), the datagram half.
  Both hand off over the iceoryx2 ring through the prebuilt wheel, and both carry no player traffic. `aioquic`
  implements QUIC and TLS 1.3 in Python from the RFCs, so it shares no code with the picoquic the C pair vendors.
  Binding picoquic from Python was rejected because both ends would then run the same QUIC and the same TLS, and h2o
  because its WebTransport is an unmerged pull request against an HTTP/3 stack h2o calls experimental.
- A Python emitter in `contract-entity-packet`, so `lake exe packet_emit` writes the C header, the Python codec and the
  64 golden vectors from one run. A second implementation that retyped the layout would test whether two people can
  copy a table. Regenerating the header and the vectors produced byte-identical output, so the change perturbs nothing.
- A conformance gate in both new repositories: 64 vectors decoded, re-encoded and compared byte for byte, with a
  `--self-test` that corrupts one vector and must fail. CI runs both on every pull request and in the merge group.

## Changed

- `transport-gateway` is `transport-gateway-c` and `transport-ingest` is `transport-ingest-c`. Two implementations of
  one contract are distinguished only by how they are built, so RFD 0111's preference for names that say what a thing
  does cannot separate them. Naming the language rather than the library survives a change of library, which
  this day already exercised: the Python pair moved from `pywebtransport` to `aioquic` before it merged and neither
  name moved. Neither pair keeps the unqualified name, because the unqualified name implies the other is a variant.
  `transport-picoquic` is the precedent.
- The GitHub descriptions on both C repositories. Each read "hands the result to a **plane** over iceoryx2", a word
  RFD 0111 retired in favour of interactor. The READMEs were converted and the descriptions were missed.
- The `rfd/0062` inventory gains a transport-layers section, which it had none of, and its counts move from 73
  repositories and 49 active to 75 and 51.
- The manifest count in `fabric`'s README moves from 45 projects to 47. That count is gated, and the gate's own
  negative control hard-codes the number, so the control had to move with it or it would certify nothing.

## Fixed

- Eight stale repository references in six files across five repositories, each in its own pull request:
  `transport-fanout`, `transport-gateway-c`, `transport-ingest-c`, `interactor-ward`, `entities-gyre` and
  `datasource-queen`. `check_docs.py`'s moved-repository check found every one of them; GitHub's redirects meant
  nothing was broken, and a name that no longer says which of two implementations it means is the problem.
- A burst of ring publishes lost its oldest sample. `iceoryx2` defaults a subscriber's buffer to 2 with safe overflow
  on, so three records published back to back arrived as two. Both repositories now set the buffer explicitly and keep
  safe overflow, because `rfd/0108` requires that a lagging reader never stall the writer.

## What the second implementation cannot yet do

The live cross-test against the C pair is not written, and there is nothing to write it against. `transport-gateway-c`
and `transport-ingest-c` have no `main` and no `CMakeLists.txt`, and both READMEs say "State: not started".
`transport-ingest-c`'s copy of the transport code is a stale fork of `transport-gateway-c`'s, passing an
`h3zero_callback_ctx_t` where `h3zero_callback` casts to `picohttp_server_parameters_t` and missing the
`h3zero_declare_stream_prefix` call. That divergence is why both Python repositories consume one emitted codec instead
of two copies, and it is recorded in both `OPEN_GAPS.md` files that the shared conformance gate is itself duplicated
with nothing checking that the copies agree.

A dropped ring sample stays undetectable. `HeaderPublishSubscribe` carries a node id, a publisher id and an element
count, and no sequence number. `rfd/0108` says a subscriber whose cursor falls out of the ring receives a resync
signal rather than a gap; no such signal exists, and defining one is a wire decision rather than a transport one.
